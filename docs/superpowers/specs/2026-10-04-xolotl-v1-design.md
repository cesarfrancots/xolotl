# Xolotl v1 — Design Spec

- **Date:** 2026-10-04
- **Status:** Draft, awaiting review
- **Target model:** GLM 5.3 Flash (`glm-5.3-flash`)
- **Language:** Rust (toolchain 1.95)

## 1. Summary

Xolotl is a small terminal coding agent for GLM 5.3 Flash. v1 is a daily-driver agent: an inline terminal REPL plus a headless mode, seven tools, three permission modes, and disk-backed context management with lossless two-stage compaction.

It is built so that a Meta-Harness-style optimization loop (Lee et al., 2026) can be added in v2 without a rewrite:

- Everything that decides *what the model sees* lives in one file, `policy.rs`.
- Every session is recorded as raw, grep-friendly traces that link back to the policy version that produced them.

## 2. Goals and non-goals

**v1 goals**

1. Interactive inline terminal agent, plus a headless `-p` mode with JSON-lines output.
2. Seven tools: `read`, `write`, `edit`, `glob`, `grep`, `bash`, `todo`.
3. Three permission modes: `ask`, `writes` (default), `yolo`.
4. Session store on disk that is the source of truth for context. The agent can grep it as external memory, and it doubles as a trace archive.
5. Two-stage compaction that never deletes information. Only the prompt view changes; raw history stays on disk.
6. Clear separation between fixed plumbing and the optimizable policy (`policy.rs`).

**Non-goals for v1** (deliberately excluded)

- Web fetch, sub-agents, MCP, image input.
- Background or long-running processes such as dev servers.
- Markdown rendering, full-screen TUI, `/undo` (backups are kept, though; see §11.6).
- Providers other than an OpenAI-style chat-completions endpoint.
- The v2 search loop itself (only its hooks; see §15).

## 3. What we take from the paper

Source: *Meta-Harness: End-to-End Optimization of Model Harnesses*, arXiv:2603.28052.

| Paper finding | Where it lands in Xolotl |
|---|---|
| Full history exposed through a filesystem and read with `grep`/`cat` beats feeding compressed history into the prompt (§3). | The session store (§9) is the source of truth. The agent reads its own past with `read`/`grep`. |
| Raw traces beat summaries: 50.0 vs 34.9 median accuracy. Summaries strip out the details needed for diagnosis (Table 3). | Compaction keeps pointers to raw events. The table of contents is generated by the harness, not the model (§10.4). |
| The winning TerminalBench-2 harness = native tool calling + 30KB output cap + completion checklist + an **environment snapshot taken before the first turn** (App. B.3). | The same four ingredients (§7, §11.1, §11.3). |
| Prompt and completion-flow edits regressed. Additive information was the safe win (App. A.2). | Short system prompt that is measured rather than tweaked. Completion check fires at most once (§11.3). |
| Completion state reset by later commands caused 15–60 step verification spirals (App. A.2, iterations 2 and 4). | The completion check is never re-armed within a request. |
| Leaked-marker no-tool-call loops needed a loop breaker (App. A.2, iteration 1). | Repeated-call and empty-response guards (§11.4). |
| Log in a machine-readable, hierarchical, consistently named format, and add a small query CLI later (App. D). | JSONL events, `seq` = line number, a fixed directory layout, and a v2 CLI (§15). |
| Cheap validation before an expensive evaluation (App. D). | v2 gate: `cargo check` plus an offline scripted-model test (§14, §15). |

## 4. Target model: GLM 5.3 Flash

Facts as published (released 2026-08-26):

| Property | Value |
|---|---|
| Model id | `glm-5.3-flash` |
| Context window | 1M tokens |
| Max output | 128K tokens |
| Capabilities | Function calling, streamed tool calls, structured output, context caching |
| Thinking | Always on; cannot be disabled |
| Recommended settings | `temperature: 1`, `top_p: 0.95`, `reasoning_effort: max` |

Even with 1M tokens available, Xolotl defaults to a **200K-token working budget**. Long contexts cost more, add latency and degrade quality. Compacting rarely and in large steps keeps the prompt prefix stable, so context caching keeps hitting.

Unverified API details are listed in §16 and resolved in implementation milestone M0, before any code depends on them.

## 5. Architecture

A single binary crate with eight modules. Only `policy.rs` is optimizable; the rest is fixed plumbing.

| Module | Responsibility |
|---|---|
| `main.rs` | CLI flags, config loading, REPL, slash commands, headless entry |
| `ui.rs` | `Ui` trait plus two implementations: `Terminal` (inline, `reedline` + `crossterm`) and `Headless` (JSON lines to stdout) |
| `llm.rs` | `Model` trait plus two implementations: `ZaiClient` (SSE streaming, tool-call assembly, retries, usage) and `Scripted` (replays canned responses for tests) |
| `agent.rs` | The turn loop (§11) |
| `tools.rs` | Tool schemas and implementations |
| `perms.rs` | Modes, y/n/always prompt via `Ui`, session grants, catastrophe list |
| `store.rs` | Session directory: append/read `events.jsonl`, artifacts, summaries, `meta.json`, resume |
| `policy.rs` | **Optimizable:** system prompt, environment snapshot, view building, compaction triggers and summary prompt, table-of-contents generation, output caps, completion check, loop-guard thresholds |

**Crates:** `ureq` (blocking HTTP and streaming; no async runtime), `serde`, `serde_json`, `ignore`, `globset`, `regex`, `reedline`, `ctrlc`.

CLI flags are parsed by hand. There is no TUI framework and no tokenizer.

### 5.1 The policy contract

The v2 optimizer may rewrite `policy.rs` freely, provided these signatures stay compatible. This is the interface check from the paper's Algorithm 1.

```rust
pub fn env_snapshot_command(shell: &Shell) -> String;
pub fn system_prompt(env: &str, agents_md: Option<&str>, session_dir: &Path) -> String;
pub fn build_view(events: &[Event]) -> Vec<Message>;
pub fn estimate_tokens(events: &[Event]) -> usize;
pub fn compaction_needed(prompt_tokens: usize, budget: usize, events: &[Event]) -> Option<Compaction>;
pub fn stage2_cut(events: &[Event], budget: usize) -> Option<Cut>;   // { from_seq, to_seq, mid_turn: bool }; None = nothing to compact
pub fn summary_prompt(focus: Option<&str>) -> String;
pub fn table_of_contents(events: &[Event], session_dir: &Path) -> String;
pub fn summary_message(summary: &str, cut: &Cut, events: &[Event], session_dir: &Path) -> String;
pub fn cap_output(tool: &str, output: &str) -> Capped;   // { text, truncated: bool }
pub fn completion_check(original_request: &str) -> String;
pub const LIMITS: Limits;  // step limit, repeat threshold, recent-tool-results kept, etc.
pub const RESEND_REASONING: bool;  // set from M0 findings (§16 item 2)
```

`meta.json` records `policy_hash`, an FNV-1a hash of `include_str!("policy.rs")`, so every trace links to the exact policy that produced it.

## 6. Frontend

The frontend is **inline, not full-screen**. Output goes to the terminal's normal scrollback, so native scroll, select, copy and search keep working, and the transcript survives exit. A line editor sits at the bottom.

```
xolotl · glm-5.3-flash · D:\proj (main) · mode: writes
> fix the failing test in parser.rs
  ⋯ thinking (1.2k chars)                         ← dim, one line, updates in place
  ● grep  "fn parse_expr" src/            12 matches
  ● read  src/parser.rs:80-140
  ● bash  cargo test parser               exit 101 · 3.1s   (last 5 lines, dim)
  The test fails because the tokenizer…           ← streamed answer
  ● edit  src/parser.rs  (+3 −1)                  ← colored mini-diff
    allow edit? [y]es [n]o [a]lways ›             ← single keypress
  ● bash  cargo test parser               exit 0 · 2.8s
  ── 48.2k / 200k ctx · 7 tools · 41s ──
> _
```

- **Input** uses `reedline`. It supports multi-line entry (Alt+Enter, and multi-line paste works), a history file at `~/.xolotl/history.txt`, tab-completion for slash commands, and Ctrl+C to clear the line.
- **Reasoning** shows as a single dim line with a character count. `/think` toggles printing it in full. It is always stored in `events.jsonl`.
- **Answer text** is streamed as raw markdown.
- **Tool calls** each get one line: tool name, a short form of the arguments, and the outcome. `bash` also shows the last 5 output lines dimmed. `edit` and `write` show a colored mini-diff.
- **Permission prompts** take a single keypress: `y` / `n` / `a`.
- **Status line** prints after each request: context tokens / budget, tool-call count, elapsed time and cache-hit percentage.
- **Ctrl+C during a run** cancels the current stream or command and returns to the prompt (§12).
- **Slash commands:** `/help`, `/mode [ask|writes|yolo]`, `/compact [focus]`, `/clear` (starts a new session), `/resume [id]` (lists recent sessions if no id), `/think`, `/status`, `/exit`.

**Headless mode:** `xolotl -p "<task>"` runs a single request.

- It emits each event as one JSON line on stdout.
- Exit codes:
  - `0` — the agent finished
  - `1` — error
  - `2` — the step limit was hit
- Gated calls are decided by the mode and the `--allow` list. A call that isn't allowed is denied with a result the model can see, and the agent continues.

```rust
trait Ui {
    fn text_delta(&mut self, s: &str);
    fn reasoning_delta(&mut self, s: &str);
    fn tool_start(&mut self, call: &ToolCall);
    fn tool_end(&mut self, call: &ToolCall, result: &ToolResult);
    fn ask(&mut self, req: &PermissionRequest) -> Decision; // Allow | Deny | Always
    fn confirm(&mut self, question: &str) -> bool;          // step-limit "continue?"; Headless → false
    fn event(&mut self, e: &Event);                         // every appended event; Headless prints it as a JSON line
    fn notice(&mut self, msg: &str);                        // compaction, retries, errors
    fn status(&mut self, s: &Status);
}
```

## 7. Tools

All tools return a text result to the model. Tool failures are results, never crashes.

| Tool | Arguments | Behavior |
|---|---|---|
| `read` | `path, offset?, limit?` | Returns numbered lines. Defaults to 2000 lines; lines over 2000 chars are cut. Binary detection: a NUL byte in the first 8KB returns `binary file, N bytes`. Records the file's read time and mtime for `edit`/`write`. |
| `write` | `path, content` | Creates parent directories. If the file already exists, it must have been `read` this session and be unchanged since (mtime check). |
| `edit` | `path, old, new, replace_all?` | See §7.1. |
| `glob` | `pattern, path?` | `ignore` walker (respects `.gitignore`) plus `globset`. Newest first, capped at 200 paths. |
| `grep` | `regex, path?, glob?, mode: files\|content, context?` | Rust `regex` syntax (no lookaround; the tool description says so). Respects `.gitignore`. Caps: 200 files or 200 matches, matched lines cut at 300 chars. |
| `bash` | `command, timeout?` | Fresh process per call, started in the project root. Timeout defaults to 120s, max 600s. On timeout, kills the process tree and returns partial output plus `timed out after Ns`. Returns exit code, duration and combined stdout/stderr. |
| `todo` | `items[{text, status: pending\|in_progress\|done}]` | Replaces the whole list. Shown in the UI. Included in every compaction table of contents. |

When the model returns several tool calls in one response, they run sequentially, in order.

### 7.1 `edit` matching

1. The file must have been `read` this session and be unchanged since (mtime check). Otherwise the result is the error `file changed since read — read it again`.
2. **Line endings:** if the file uses CRLF, `\n` in `old` and `new` is converted to `\r\n` before matching. The file's line endings are always preserved.
3. **Exact match:**
   - Exactly one occurrence: replace it.
   - Several occurrences and `replace_all` is not set: error with the matching line numbers.
   - `replace_all` set: replace all occurrences and report the count.
4. **If there's no exact match, try a whitespace-trimmed line match:**
   - Compare `old`'s lines, trimmed, against windows of the file's lines, also trimmed.
   - If exactly one window matches, replace those file lines with `new`.
   - The result says `applied with whitespace-insensitive match at lines X–Y`.
5. **If neither matches:** the error lists the line numbers where the trimmed first line of `old` appears, or says that no line contains it.
6. **Writing:** write to a temp file in the same directory, then rename it over the original. The previous contents are saved first to `artifacts/<call-id>.before`.

### 7.2 Shell selection

- **Non-Windows:** `bash -lc`, falling back to `sh -c`.
- **Windows:** Git Bash, located via `where git` → `<git>\..\..\bin\bash.exe` or the standard install paths. Never use a bare `bash` from `PATH`: `C:\Windows\System32\bash.exe` is the WSL launcher. Fall back to `powershell -NoProfile -Command`.
- The environment snapshot tells the model which shell it has.

### 7.3 Output caps

Configured in `policy.rs`:

- Each tool result is capped at 30KB in context.
- For `bash`, the cap keeps the first 5KB and the last 25KB.
- When output is truncated, the full output goes to `artifacts/<call-id>.txt`, and the result ends with `[truncated: full output <size> at <abs path> — use read/grep]`.

## 8. Permissions

| Mode | `read` / `glob` / `grep` / `todo` | `write` / `edit` / `bash` |
|---|---|---|
| `ask` | asks (reads inside the session directory are always allowed) | asks |
| `writes` (default) | allowed | asks |
| `yolo` | allowed | allowed |

- **"Always" grants** last for the session.
  - For `write`/`edit`, a grant covers the whole tool.
  - For `bash`, a grant covers a command prefix: the first two words, e.g. `cargo test`.
- **Catastrophe list** — these always ask, in every mode:
  - `rm -rf` targeting `/`, `~`, `$HOME` or a drive root
  - `git push --force` / `-f`
  - `format`
  - `del /s` / `rd /s` on a drive root
- **Choosing the mode:** set with `--mode`, the config default, or `/mode` mid-session.
- **Headless mode:** a gated call that the mode and `--allow` list don't permit is denied without prompting.
- **Recording:** each decision is written as a `permission` event.

## 9. Session store (the filesystem)

```
~/.xolotl/
  config.json
  history.txt
  projects/<project-slug>/                 slug = absolute cwd with :\/ → '-', e.g. D--Xolotl-Harness
    sessions/<YYYYMMDD-HHMMSS>-<4hex>/     UTC; sortable
      meta.json                            id, cwd, git HEAD, model, mode, policy_hash, started/ended, status
      env.txt                              environment snapshot at session start
      events.jsonl                         append-only; source of truth
      artifacts/<call-id>.txt              full output of truncated tool results
      artifacts/<call-id>.before           file contents before each edit/write
      summaries/<n>.md                     stage-2 summaries (including the table of contents)
```

### 9.1 Events

Every event is one compact JSON line with `seq`, `t_ms` (unix milliseconds) and `type`.

**Invariant:** `seq` equals the event's 1-based line number. Every pointer is therefore a plain `read events.jsonl offset=<seq> limit=<n>`.

| `type` | Fields |
|---|---|
| `session_start` | `cwd, model, mode, policy_hash, system` (the full system prompt, so the trace shows exactly what the model saw and `build_view` stays a pure function of the events) |
| `user` | `text` |
| `assistant` | `text, reasoning, tool_calls[{id, name, args}], usage{prompt, completion, cached}, finish_reason, latency_ms, effort?, think_ms?` (`effort`: the `reasoning_effort` sent, absent when none was; `think_ms`: ms of reasoning before the first content or tool-call token, or the whole call if none came) |
| `tool_result` | `call_id, name, ok, output` (capped), `artifact?, bytes, duration_ms, exit_code?` |
| `permission` | `call_id, decision: allow\|deny\|always, by: user\|rule\|mode` |
| `compaction` | `stage: 1\|2, upto_seq` (stage 1), `from_seq, to_seq, summary_path, summary, tokens_before` (stage 2; `summary` is the full text placed in the view) |
| `nudge` | `reason: completion_check\|repeat\|empty, text`. A harness-written message; `build_view` renders it as a user-role message. |
| `interrupt` | `during: stream\|tool, call_id?` |
| `error` | `kind, message, retry` |
| `session_end` | `status` |

**Writes:**
- Each event is written, then the file is flushed, before the next step proceeds.

**Resume** (`--resume`, `/resume`):
- If the file doesn't end in a newline, it is truncated back to its last complete line. This keeps the `seq` = line invariant.
- Any `tool_call` without a matching `tool_result` gets a synthetic `tool_result` with `interrupted (session resumed)`.

## 10. Context management and compaction

### 10.1 The prompt view

`policy::build_view(events)` builds the messages for every model call:

```
system:  static prompt + AGENTS.md (≤20KB, from project root) + env snapshot   ← stable, cached prefix
user:    [summary + table of contents from latest stage-2 compaction]           ← only after stage 2
…        events after the latest stage-2 range, verbatim,
         with stage-1 stubs applied to tool results at or before upto_seq
```

**Invariant:** every assistant `tool_call` in the view has exactly one matching tool result. This holds after interrupts, resumes and compactions. The API rejects requests that violate it.

### 10.2 Measuring size

- The current size is the last response's `usage.prompt_tokens + usage.completion_tokens`, plus `chars / 3` for each event appended since. `chars / 3` deliberately overestimates for code.
- If a compaction happened after the last response, that usage is stale. The size is then `chars / 3` of the whole current view.
- The budget `B` defaults to 200K and is configurable with `--budget` or the config file.

### 10.3 Stage 1 — shrink old tool output (no LLM call)

- **Trigger:** size ≥ 60% of `B`, and at least 11 `tool_result` events exist since the latest stage-2 range. Stage 1 is skipped if there are fewer than 11.
- **Action:** append `compaction{stage: 1, upto_seq}`, where `upto_seq` is the `seq` of the 11th-most-recent `tool_result`.
- **Effect:** from then on, `build_view` replaces each tool result at or before `upto_seq` with a stub:
  `[elided: 14KB bash output — events.jsonl seq 233; full: artifacts/c33.txt]`
  The artifact part appears only if one exists. `todo` results are never stubbed.
- **Why the cutoff is fixed:** it moves only when stage 1 fires again, so the prompt prefix stays stable between compactions.

### 10.4 Stage 2 — summary with pointers

**Triggers** (any one of these):
- size ≥ 85% of `B`
- the most recent compaction was stage 1, and the next response's size is still ≥ 60% of `B` (so stage 1 never fires twice in a row)
- size ≥ 60% of `B`, and stage 1 was skipped
- `/compact [focus]`
- the API reports a context overflow (stage 2 runs, then the request is retried once)

**Procedure:**

1. **Choose the cut** with `policy::stage2_cut`. `from_seq` is the event after the previous stage-2 range, or 1. `to_seq` is the first of these whose kept part (estimated `chars / 3`) is ≤ 40% of `B`:
   - **A:** just before the second-to-last `user` event (keeps the last two user turns verbatim)
   - **B:** just before the last `user` event
   - **C:** mid-turn — just before an `assistant` event: the earliest one whose kept part is ≤ 20% of `B`, or else the last `assistant` event

   A cut always lands right before a `user` or `assistant` event, so it never separates a tool call from its result. A cut only counts if `from_seq..=to_seq` contains at least one `user` or `assistant` event. If no cut qualifies, there is nothing to compact. Option C exists because a single request often turns into 100+ tool calls, and then A and B would keep almost everything.
2. **Summary call:** the current view plus `policy::summary_prompt(focus)`, sent with tools disabled. The model writes markdown with these sections:
   - Goal
   - Current state
   - Decisions and why
   - Files touched
   - Failed attempts and why they failed
   - Open TODOs and next step
3. **Table of contents:** `policy::table_of_contents` appends one, built by the harness rather than the model, so its pointers can't be hallucinated. It lists:
   - every `user` message verbatim, up to its first 500 chars, with its `seq`
   - every edited or written file, with the `seq` of each change
   - every artifact path
   - the current `todo` list
   - the absolute path of `events.jsonl`
4. **Mid-turn cut:** if the cut was C, the active request (the last `user` event before the cut) is appended in full under `## Current request (verbatim)`. Otherwise the model would lose its task.
5. Write it to `summaries/<n>.md` and append `compaction{stage: 2, from_seq, to_seq, summary_path, summary, tokens_before}`.
6. If the summary call fails, append an `error` event, show a notice, and leave the view unchanged. Compaction is never allowed to crash the session.

Nothing is ever deleted. Compaction only changes the view; raw history stays in `events.jsonl` and `artifacts/`.

## 11. Agent loop

For each user request:

1. Append a `user` event.
2. Repeat:
   1. Build the view.
   2. Stream the model call, forwarding deltas to the `Ui`.
   3. Append the `assistant` event.
   4. Run each tool call: permission check, run, cap output, append `tool_result`.
   5. Check the compaction triggers.
   6. Check the loop guards.

   The loop ends when the model replies without tool calls and no completion check fires, or when the step limit or an interrupt stops it.
3. Print the status line.

Harness-written messages (the completion check, repeated-call notes, empty-response nudges) are appended as `nudge` events. That way the trace records exactly what the model saw.

### 11.1 Environment snapshot

At session start, run `policy::env_snapshot_command` once.

- **Constraints:** a single compound shell command with a 15s timeout. It fails silently: on error or timeout the snapshot is just shorter.
- **Contents:**
  - OS and shell, cwd
  - git branch, `git status --short` (≤20 lines), last 5 commits
  - top-level listing (≤30 entries)
  - detected manifests (`Cargo.toml`, `package.json`, `pyproject.toml`, `go.mod`, `Makefile`, …) and the build/test commands they imply
  - versions of `rustc`, `cargo`, `node`, `python`/`py`, `go`, `java`, `gcc`
  - available memory
- **Output:** included in the system prompt and saved to `env.txt`.

### 11.2 System prompt

Short, and kept in `policy.rs`. It covers:

- the role
- read before edit; prefer `edit` over `write`
- use `todo` for multi-step work
- verify with build/tests
- don't start long-running processes
- the session directory path, and that past details can be recovered with `read`/`grep` on `events.jsonl` and `artifacts/`

Changes to it are meant to be measured in v2, not tuned by feel.

### 11.3 Completion check

- **Trigger:** the model replies without tool calls, at least one `edit`/`write` succeeded during this request, and no check has fired yet for this request.
- **Action:** append a `nudge{reason: completion_check}` whose text is `policy::completion_check(original_request)`. It contains the original request verbatim and asks: did you build/test; is any debug or temp leftover; summarize what changed.
- **Guard:** at most once per request. Later tool calls never re-arm it.

### 11.4 Loop guards

- **Step limit:** 100 model calls per request. Interactive mode then asks whether to continue; headless mode exits with code `2`.
- **Repeated calls:** if the same `(tool, args)` repeats 3 times in a row with identical results, append `nudge{reason: repeat}`: `this call returned the same result 3 times — change approach`.
- **Empty responses:** after an empty response (no text, no tool calls), append `nudge{reason: empty}` and call again once. If the reply is empty again, the request ends with an error notice.

### 11.5 Model parameters

`temperature`, `top_p` and `reasoning_effort` come from config. Defaults follow Z.ai's published recommendation (§4), to be confirmed in M0.

### 11.6 File safety

- `edit` and `write` use temp file + rename.
- The previous contents are saved to `artifacts/<call-id>.before` before every change.

## 12. Error handling

| Failure | Behavior |
|---|---|
| HTTP 429 / 5xx / network | Exponential backoff 1, 2, 4, 8s (honoring `Retry-After`), 5 attempts max, then an `error` event and back to the prompt |
| Context overflow (400) | Forced stage-2 compaction, retry once |
| Auth error (401/403) | Fail fast: `check <api_key_env>` |
| Malformed tool-call argument JSON | `tool_result{ok: false, "invalid JSON arguments: …"}` so the model can fix the call |
| Unknown tool name | `tool_result{ok: false, "unknown tool …; available: …"}` |
| Ctrl+C during stream | Stop reading the stream. The assistant message is kept with `[interrupted]`. Any tool calls it contained get `cancelled by user` results. Append `interrupt`. |
| Ctrl+C during tool | Kill the process tree (`taskkill /T /F /PID` on Windows; process group on Unix). The result is `cancelled by user` plus partial output. Remaining calls are cancelled. |
| Crash | Events are already flushed; `--resume` repairs and continues (§9.1) |

## 13. Configuration

**Precedence:** CLI flags > environment > `~/.xolotl/config.json` > defaults.

The API key is **only** read from the environment variable named by `api_key_env`. It is never written to disk or into any event.

```json
{
  "base_url": "https://api.z.ai/api/paas/v4",
  "model": "glm-5.3-flash",
  "api_key_env": "ZAI_API_KEY",
  "context_budget": 200000,
  "mode": "writes",
  "temperature": 1.0,
  "top_p": 0.95,
  "reasoning_effort": "max"
}
```

**Flags:**
- `-p <prompt>`
- `--mode <ask|writes|yolo>`
- `--cwd <dir>`
- `--resume [id]`
- `--budget <tokens>`
- `--allow <bash-prefix>` (repeatable)
- `--model <id>`

## 14. Testing

**Unit tests** (`#[cfg(test)]` in each module):

- **`edit`:** unique match; ambiguous match error; `replace_all`; whitespace-trimmed fallback; CRLF preservation; stale file rejected; `.before` backup written.
- **Output caps:** head/tail split; artifact written; truncation note format.
- **`build_view`:** stage-1 stubs only at or before `upto_seq`; `todo` never stubbed; the stage-2 summary replaces exactly `from_seq..=to_seq`; tool-call/result pairing holds after interrupt, resume and both compaction stages.
- **Store:** `seq` = line number; resume truncates a partial last line; dangling tool calls get repaired.
- **Permissions:** mode × tool matrix; `bash` prefix grants; catastrophe list asks in `yolo`; headless denials.
- **Shell:** Windows resolution never picks `System32\bash.exe`.

**Offline integration tests** use `llm::Scripted`. They run the full loop against a temp directory:

- read → edit → completion check fires once → done
- interrupt mid-stream
- a small `--budget` that forces both compaction stages

**Live smoke test** (`#[ignore]`, run with `cargo test -- --ignored`): GLM creates `hello.txt` containing `hi` in a temp directory.

**Acceptance:** Xolotl makes a real change to its own repository.

## 15. v2 hooks

These are built into v1, but no v2 code ships in v1:

- Headless mode with JSON lines, exit codes, `--mode`, `--cwd` and `--allow` lets an eval runner drive Xolotl.
- `meta.json` carries `policy_hash`. v2 adds `score.json` per evaluated session.
- `llm::Scripted` can replay recorded traces.

**Planned v2 layout** (paper App. D):

```
~/.xolotl/search/<run>/candidates/<id>/{policy.rs, check.log, scores.json, sessions/…}
```

It comes with a small CLI to list the Pareto frontier and the top-k candidates, and to diff two candidates' code and results.

**v2 loop:**

1. A proposer (e.g. Claude Code with a skill file that says only `policy.rs` may be edited) reads the store and writes a candidate `policy.rs`.
2. The candidate must pass `cargo check` and the offline scripted tests.
3. Survivors run on a small, hard coding task set.
4. Candidates are kept on a pass-rate × tokens Pareto frontier.

## 16. Open items to verify in M0

Each is verified with a direct API call before the code that depends on it is written:

1. Base URL for the international API and for the Coding Plan endpoint, and which one the user's key belongs to.
2. Whether `reasoning_content` from earlier assistant turns should be sent back (the GLM 4.7 series had "preserved thinking"), both within a tool-call loop and across user turns. `build_view` makes this a policy switch.
3. Streamed tool-call delta format: index-based partial `arguments` like OpenAI, or whole calls per chunk.
4. Usage field names, including where cached-token counts are reported.
5. Accepted `reasoning_effort` values and the default.
6. The exact error code and message for a context overflow.
7. Whether multiple tool calls per response occur, and whether `parallel_tool_calls` exists. Xolotl handles multiple calls sequentially either way.
8. Whether a request whose history contains tool calls is accepted without a `tools` parameter. The tools-disabled summary call (§10.4) depends on this. If it isn't, send the tools with `tool_choice: "none"` instead.
